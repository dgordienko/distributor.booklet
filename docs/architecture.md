# Архитектура

## Компоненты

| Компонент | Кто пользуется | Что делает |
| --- | --- | --- |
| **backend** | admin-web, android | REST API (`/api/*`), раздача загруженных файлов (`/uploads/*`), хранение в SQLite через Prisma, синхронизация команд из внешнего API устройств |
| **admin-web** | администратор каталога | SPA за входом Auth0: товары, фото, категории (разделы буклета), команды, обложка |
| **android** | покупатель в торговой точке | Читает каталог без авторизации и показывает его как листаемый буклет |

В продакшене admin-web и backend работают в двух Docker-контейнерах. Наружу
открыт только контейнер админки: его nginx отдаёт SPA и проксирует `/api` и
`/uploads` на backend. Подробно: [deploy/DEPLOY.md](../deploy/DEPLOY.md).

```
https://dswapi.online/booklet/  ─► общий nginx (TLS) ─► booklet-admin:8080
                                                           ├─ /            SPA
                                                           ├─ /assets/     статика (кеш 1 год)
                                                           ├─ /api/    ─► booklet-backend:4000
                                                           └─ /uploads/ ─► booklet-backend:4000
```

## Модель данных

Схема: [`backend/prisma/schema.prisma`](../backend/prisma/schema.prisma).

```
Brand (одна строка, id = 1)        обложка: name, tagline, logoUrl

Category ──< ProductCategory >── Product ──< Photo
   │            (order)            │           (isPrimary)
   └──< >── Team                   └─ isActive
```

- **Brand** — настройки обложки буклета. Всегда одна запись с `id = 1`,
  создаётся при первом обращении.
- **Category** — раздел буклета: страница-разделитель (изображение, название,
  описание) и товары раздела. `order` задаёт порядок разделов.
- **Product** — товар: название, описание (HTML из редактора), производитель,
  торговая марка, тип, срок и температура хранения, состав, цена и валюта
  (по умолчанию `UAH`). `isActive = false` скрывает товар с планшета.
- **ProductCategory** — связь «многие ко многим». Один товар может входить в
  несколько разделов (например, ещё и в «Акционное предложение»). Порядок
  товара (`order`) свой в каждом разделе, поэтому хранится на связи.
- **Photo** — фото товара. Первое загруженное фото становится главным
  (`isPrimary`). Если удалить главное, главным становится следующее.
- **Team** — мобильная команда (`frcId`, `frcName`) из внешнего API устройств.
  Категория без команд считается общей, категория с командами предназначена
  только им.

Файлы (фото, изображения разделов, логотип) лежат в `UPLOADS_DIR`, а в базе
хранится относительный путь вида `/uploads/<имя-файла>`. Клиенты сами
дописывают к нему базовый адрес.

## Как собирается буклет на планшете

Порядок страниц формирует Android-приложение из ответов API:

1. **Обложка** — бренд: логотип, название, слоган.
2. Для каждой категории по возрастанию `order`:
   - страница-разделитель категории;
   - сетки товаров этой категории по 6 на страницу, в порядке `order` из
     `ProductCategory`.
3. **Товары без категории** — в конце, без разделителя.

Показываются только товары с `isActive = true`. Товар, входящий в несколько
категорий, появляется в каждом своём разделе. Тап по плитке открывает
полноэкранную карточку. В режиме карточек каждый товар встречается один раз,
и их можно листать.

## Авторизация

| Запрос | Кто делает | Защита |
| --- | --- | --- |
| `GET`/`HEAD` под `/api`, `GET /uploads/*` | android, admin-web | Открыты: планшет читает каталог без входа |
| `POST`/`PUT`/`PATCH`/`DELETE` под `/api` | admin-web | Auth0 access-токен (JWT) в `Authorization: Bearer` |
| Интерфейс админки | администратор | Вход через Auth0 (`@auth0/auth0-react`) |

- admin-web запрашивает токен для API с audience `VITE_AUTH0_AUDIENCE` и
  добавляет его ко всем запросам, кроме GET.
- backend проверяет подпись, издателя (`AUTH0_ISSUER_BASE_URL`) и audience
  (`AUTH0_AUDIENCE`) через `express-oauth2-jwt-bearer`.
- Если Auth0 в backend не настроен, запись закрыта и отвечает `503`. Для
  локальной разработки есть явный флаг `AUTH_DISABLED=true`, на сервере его
  задавать нельзя.

## Префикс публикации

Админка умеет работать не от корня домена. Префикс (`BASE_PATH`, например
`/booklet/`) задаётся при сборке. От него зависят `base` в Vite, `basename`
роутера, адрес API, ссылки на `/uploads/...` и `redirect_uri` в Auth0. Без
префикса всё работает от корня, как в локальной разработке.
